## 一、原文完整中文翻译

### 第 1 段：自回归推理的瓶颈与推测解码

大语言模型（Large Language Models，LLMs）以自回归（Autoregressive）方式生成文本：每生成一个新 Token，都需要基于此前所有 Token 执行一次完整的前向传播，这使得推理延迟与输出长度成正比。

由此造成的 GPU 利用率偏低以及用户感知等待时间较长，已经成为生产环境中 LLM 服务的主要瓶颈，尤其是在实时对话助手、多轮智能体工作流等对延迟敏感的场景中。

推测解码（Speculative Decoding；Chen et al., 2023；Leviathan et al., 2023）提供了一种具有严格理论依据的解决方案：一个轻量级草稿模型首先提出一组候选 Token，随后完整规模的目标模型通过拒绝采样（Rejection Sampling），在单次前向传播中验证整个候选块，接受其中与目标分布一致的最长前缀，并额外附加一个 Bonus Token。

由于验证过程可以并行执行，而且接受规则能够精确保持目标模型的概率分布，因此推测解码可以在不损失生成质量的情况下加速推理。

### 第 2 段：自回归与并行草稿模型的取舍

草稿模型的设计决定了草稿生成延迟与接受率之间的权衡。

早期的草稿模型采用自回归方式（Cheng et al., 2024；Li et al., 2024b），每个位置的预测都依赖此前已经采样的 Token。

然而，这种方法的草稿生成延迟会随着块大小线性增长，迫使这些方法采用较短的草稿块和较浅的模型架构。

为了突破这一串行瓶颈，并行草稿模型（Parallel Drafters；Cai et al., 2024；Chen et al., 2026；Liu et al., 2026a）成为一种很有吸引力的替代方案：所有草稿位置都在单次前向传播中生成，使草稿生成延迟几乎不受块大小影响。

这种结构上的优势，从理论上允许并行草稿模型高效地生成明显更长的候选 Token 块。

### 第 3 段：并行草稿模型的两大瓶颈

然而，要充分释放大型并行草稿块的潜力，还面临两个关键瓶颈：一个来自生成质量，另一个来自系统效率。

首先，由于并行草稿模型独立预测各个位置，它们无法建模块内 Token 之间的依赖关系。这种独立性会导致多模态碰撞（Multi-modal Collisions），以及后续位置接受率的迅速下降（Gu et al., 2018；Huang et al., 2022b）。

其次，如何确定最优验证长度仍然具有挑战性。尽管并行生成可以轻易地产生较长的草稿块，但不加区分地验证所有候选 Token，会降低系统吞吐量，尤其是在高并发工作负载下（Hu et al., 2026b；Liu et al., 2024c）。

理想的验证长度会沿着两个维度发生变化。

在数据维度上，代码等结构化请求天然能够维持比开放式聊天更高的接受率（Abramovich et al., 2026；Xia et al., 2024）。

在系统维度上，系统负载较轻时，验证额外 Token 几乎不需要付出额外代价。

但在高负载条件下，验证拒绝风险较高的 Token 会占用关键的批处理容量，而这些容量原本可以用于服务其他正在执行的请求（Liu et al., 2024b；Wu et al., 2025）。

### 第 4 段：提出 DSpark

为了解决上述瓶颈，我们提出 DSpark，这是一种将高吞吐并行生成与自适应、负载感知验证相结合的推测解码框架。

DSpark 的核心设计目标，是通过两种互补机制，解决草稿生成与验证之间固有的权衡问题。

**贡献 1：半自回归生成（Semi-Autoregressive Generation）。**

首先，为了克服 Token 之间缺乏依赖关系的问题，DSpark 采用半自回归架构。

它保持计算开销较大的草稿主干网络完全并行，仅在输出端增加一个轻量级串行预测头，用于引入局部 Token 转移信息。

这种设计在保留并行模型草稿生成速度的同时，显著缓解了后缀质量衰减。

**贡献 2：置信度调度验证（Confidence-Scheduled Verification）。**

其次，为了解决系统层面的瓶颈，DSpark 引入置信度调度验证机制。

通过将一个置信度预测头（Confidence Head）与硬件感知调度器（Hardware-Aware Scheduler）结合，DSpark 可以动态调整每个请求的验证长度。其中，置信度预测头负责估计各个位置的前缀存活概率。

该调度器利用实时的引擎吞吐性能曲线，将目标模型的验证预算优先分配给预期收益最高的 Token。

### 第 5 段：离线基准测试结果

我们在受控离线基准测试和生产规模的在线部署环境中，对 DSpark 进行了广泛评估。

在涵盖数学推理、代码生成和日常聊天的受控离线基准测试中，DSpark 始终优于具有竞争力的基线方法。

具体而言，在 Qwen3-4B、8B 和 14B 目标模型（Yang et al., 2025）上，相较于自回归草稿模型 Eagle3（Li et al., 2026b），DSpark 的宏平均接受长度分别提高了 **30.9%、26.7% 和 30.0%**；相较于并行草稿模型 DFlash（Chen et al., 2026），则分别提高了 **16.3%、18.4% 和 18.3%**。

除了整体指标之外，我们针对不同草稿位置进行的细粒度分析，揭示了不同草稿模型各自的生成特性，并通过实验证明：DSpark 成功结合了并行模型在初始 Token 位置的高预测能力，以及自回归模型在后续位置上的连贯性优势。

### 第 6 段：DeepSeek-V4 线上部署结果

除了离线评估之外，我们还将 DSpark 部署到 DeepSeek-V4（DeepSeek-AI, 2026）服务系统中，以评估其在真实用户流量下的性能。

与此前的 MTP-1 生产环境基线（DeepSeek-AI, 2024）相比，DSpark 显著扩展了系统的可运行性能范围。

具体而言，在总吞吐能力相同的条件下，DSpark 稳定地将单用户生成速度提升了 **60%～85%（V4-Flash）** 和 **57%～78%（V4-Pro）**。

此外，在严格的服务等级协议（Service Level Agreements，SLAs）约束下，例如 Flash 的 120 TPS 和 Pro 的 50 TPS，基线系统的处理能力会严重下降，而 DSpark 能够通过减少验证开销维持稳健的吞吐能力。

通过克服这种性能悬崖（Performance Cliff），DSpark 实现了此前无法达到的严格交互性能等级，从而有效推动了 LLM 服务系统的帕累托前沿。

## 二、深度技术分析（独立分析，非原文）

### 1. 为什么 Draft 的速度和质量是一个共同优化问题？

推测解码通常在每轮先生成 \`γ\` 个候选，再调用目标模型一次并行验证。在正式的 Section 2，论文用 \`L=(T_draft+T_verify)/τ\` 描述平均生成 Token 的延迟。此处先解释参数含义：\`T_draft\` 是草稿生成墙钟耗时，\`T_verify\` 是目标验证耗时，\`τ\` 是每轮平均有效生成的 Token 数（论文习惯包含 bonus token）。这是**对后续 Section 2 的预读**，不是 Section 1 给出的编号公式。

增加 Block Size 并不保证 \`τ\` 同比例增长，因为任一早期拒绝都会使其后的候选无法直接接受；更深的 AR Draft 虽可能更准确，但为了构造较长草稿需要多轮串行计算；并行 Draft 可增加 Backbone 深度而不线性增加串行步数，但面临后缀衰减。

### 2. 多模态碰撞及后缀衰减

若一个前缀存在不同、各自合理的未来序列，比如后续 Section 3.1 所举的 “of course” 和 “no problem”，单次并行预测各位置的边缘分布可能产生 “of problem” 或 “no course”。这些混合序列每个位置孤立看似合理，但联合起来不连贯。此例来自 Section 3.1，是用来阐释 Introduction 所述现象的**后文预读**。

形式化地，纯并行简化假设可以表述为对固定上下文 \`C\`：
\`q_parallel(x_{1:γ}|C)≈∏_{k=1}^γ q_k(x_k|C)\`。
自回归则采用 \`q_AR(x_{1:γ}|C)=∏_{k=1}^γ q_k(x_k|C,x_{<k})\`。
两者的差异不是能不能一次性算多个概率，而是后续分布是否能根据已采样的同块 Token 更新。DSpark 保持并行 Backbone，同时增加廉价的因果输出头。这个公式是教学抽象，不是 Section 1 原文或 DSpark 的精确定义；详细机制参见 Section 3.1 的 Equation (4)–(6)。

### 3. 为什么高负载时不应该验证所有候选？

推测解码的接受遵守连续前缀规则。在后续 Section 3.2 中，定义第 \`k\` 个位置在前缀全接受条件下的概率为 \`c_k\`，则长度为 \`j\` 的前缀存活概率 \`a_j=∏_{i=1}^j c_i\`。对一个请求，如果验证长度为 \`ℓ\`，预期产生 Token 数是 \`1+Σ_{j=1}^ℓ a_j\`。若额外位置的 \`a_j\` 极小，则占用一次目标验证的额外 token-slot 的边际回报也很低。

例：\`c=[0.9,0.8,0.4,0.3]\` 时，\`a=[0.9,0.72,0.288,0.0864]\`；验证前两位的预期输出为 \`2.62\`，验证完整四位的预期输出为 \`2.9944\`。多用 2 个验证槽位，仅增加约 \`0.3744\` 个预期输出 Token。数值纯属演示，**不是论文实验数据**。

**关键系统级差异：** 低负载时 GPU 可能有大量空余并行能力，增加 token-slot 的实际墙钟开销较小；高负载时这些槽位与其他请求竞争批处理容量，必须从整个 GPU 的总吞吐收益而不只是单请求 \`τ\` 决策。引言明确指出这一数据维度×负载维度的联合问题。

### 4. 硬件感知调度的目标与适用前提

Section 3.2.2 把 GPU 在不同 token batch size \`B\` 下的 engine SPS（steps per second）预先 profile 成表，选取逐请求的长度以最大化 \`Θ=τ×SPS(B)\`。这个式子属于**后续正文预读**，引言只陈述了按实时吞吐曲线动态分配验证预算的思想。不同硬件、CUDA Graph、kernel、当前排队请求数会改变容量曲线，故不是单一固定置信度阈值能够通吃。

另外，动态调度不能根据尚未合法观察到的未来 Token 选择前缀，否则会违反保持目标概率分布所需的 non-anticipating property。该性质与论文 Appendix A 的反例、Section 5.2 异步调度实现有联系；Introduction 尚未展开其证明。

## 四、小结与下一阅读位置

Introduction 核心逻辑是：AR Drafter 质量高但串行成本大；并行 Drafter 速度快但块内一致性差；固定长块验证在高并发下有机会成本；DSpark 用半自回归提高候选质量，并用置信度+硬件吞吐曲线分配目标验证预算，在离线实验和线上生产环境分别验证两类收益。
